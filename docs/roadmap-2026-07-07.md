# Implementation roadmap, 2026-07-07

Task 3 of the July plan. Status: APPROVED 2026-07-09. Maor answered the open
questions: backup off-box target = both (DO backups + pulls to the home PC),
liveness = healthchecks.io, license = MIT, docs committed. Implementation
started the same day with wave A (0.1 first). Question 4 (quiz-bank file
delivery) stays open until the friend's file arrives; question 5 (phase-5
green light) is deferred until waves A-B are done.

This replaces docs/ROADMAP.md (frozen 2026-06-11) as the single "what's next"
document; retiring the old file is itself a roadmap item (2.4). Inputs: the
state report (docs/state-of-project-2026-07-07.md), the audit
(docs/project-audit-2026-07-07.md, whose closing section fixed the ordering
used here), the hermes feature survey
(docs/research/2026-06-10-hermes-feature-survey.md) for the new-capability
menu, and the project memory (billing and hosting decisions).

How to use it: one item is one focused session ending in one PR. At
implementation time each code item gets its own detailed plan (brainstorming
for the design-shaped ones, then a written task plan, TDD throughout, code
review before merge), so this document stays at the "what and why" level and
names files, not line-by-line steps.

Effort scale (same as the survey): S = under a day, M = 1 to 3 days,
L = multi-day.

## How items were weighed

1. The audit's ordering is the spine: continuity fixes are table stakes, then
   cost, then the portfolio storefront, then the quiz bank, and only then new
   capabilities.
2. New capabilities are ranked by the project rule: daily usefulness times
   demo value (the repo doubles as a CV piece).
3. The unused-surface data steers what NOT to build: one monitor in use, the
   calendar-event-check skill at 0 uses, 1 opus call out of 156. More surface
   is not the goal; visible reliability and a few strong stories are.

## Phase 0: continuity (the audit's Tier-1 trio)

The theme: today a droplet loss erases the agent's accumulated state, a silent
death goes unnoticed until Maor wonders why it stopped answering, and a
rebuild from the runbook would come up without its safety hook. All three
fixes are small.

### 0.1 Nightly backup of agent state, with an off-box copy

What: a backup script on the droplet (backup.sh or backup.ts plus a systemd
timer) that runs sqlite's .backup on bot.db (correct under WAL), tars it with
the json state files (reminders, followups, choices, pending, cal_notified,
quiz-state), the skills/ and memory-mirror markdown, and data/questions.json,
into a dated archive under ~/backups with 14-day rotation. uploads/ is
excluded by default (500MB cap, replaceable content).

Off-box layer, Maor picks one (open question 1):
- DigitalOcean droplet snapshots, whole-disk, hands-off, about 20% of droplet
  cost per the audit (a few dollars a month).
- A scheduled pull from this Windows machine over scp (free, but only as
  reliable as the machine being on).
- Both (snapshots weekly, local rotation nightly) is the comfortable answer.

Includes a documented restore drill in DEPLOY.md (restore to a scratch dir,
open the db, count rows). A backup that has never been restored is a hope,
not a backup.

Where: new backup script + systemd timer unit, DEPLOY.md section.
Effort: S. Verify: run the timer once, restore the archive on the droplet and
on Windows, compare table counts. Depends: nothing.

### 0.2 External liveness alerting

What: a dead-man check that lives off the droplet, because the failure it
must catch is the droplet (or the poller, or Telegram polling) dying silently.
The 2026-06-20 token expiry went unnoticed for about 28 hours; that is the
benchmark to beat.

How: a healthchecks.io-style free dead-man endpoint (open question 2 covers
the account). Two pings:
- The poller pings after each healthy getUpdates cycle (proves the service,
  the network, and Telegram polling all work), throttled to every few minutes.
- The nightly [AUTO] job pings a second slug on success (proves the claude
  spawn path works, which catches an expired OAuth token even while polling
  looks healthy).
If pings stop, Maor gets an email (and optionally a Telegram notification
from the service's own integration, which usefully does not depend on our
agent being alive).

Where: poller.ts (a few lines at the poll loop and the [AUTO] completion
path), .env on the droplet (ping URLs), DEPLOY.md.
Effort: S. Verify: stop the service, watch the alert arrive; renew and watch
it clear. Depends: a free account on the chosen service.

### 0.3 Close the fresh-install gap on the guard hook

What: the audit verified that DEPLOY.md never mentions the PreToolUse guard
hook, and hooks/README.md describes wiring it into the tracked
.claude/settings.json while production actually carries it in the untracked
settings.local.json. A rebuild from the runbook would produce an agent with
full Bash and no hardline floor, and nothing would notice.

How, three parts:
1. A DEPLOY.md step with the exact settings.local.json snippet.
2. Align hooks/README.md with the live wiring (keeping the hook in
   settings.local.json is the recommendation: moving it into the tracked file
   would also apply it to dev sessions on the Windows machine, which is a
   behavior change to decide separately, not silently).
3. A startup self-check: at boot the poller verifies the settings file
   registers hooks/pretooluse-guard.ts, and on failure logs loudly and sends
   Maor a one-line warning. This turns a silent gap into a nagging one.

Where: DEPLOY.md, hooks/README.md, poller.ts startup, a small test for the
checker.
Effort: S. Verify: temporarily unregister the hook on a scratch checkout and
watch the warning fire. Depends: nothing.

## Phase 1: cost and telemetry

The theme: scheduled jobs are 29% of spend and run on Sonnet for formulaic
work, and the meter that exists to answer "what does the agent cost" has a
permanent blind spot. Worth doing before Anthropic's credit split lands.

### 1.1 Route scheduled jobs to Haiku

What: kind=auto is 37 calls, $5.18, 29% of all spend since June 16, and
produces more output tokens than the entire interactive history (the nightly
summary and channel digest are long-form). These are summarization jobs; the
review loop already runs happily on haiku, so the model id and the mechanism
are proven in this exact codebase.

How: add "haiku" to the Model union in model.ts, and give the [AUTO] spawn
path in poller.ts a per-job model choice defaulting to haiku for scheduled
jobs, with a simple override for any job that turns out to need Sonnet.
Interactive routing is untouched. Same change pins the output language of the
nightly summary and digest prompts (the one-off Spanish summary of 2026-07-06
gets closed for free). Verify actual haiku pricing at implementation time
rather than assuming a ratio; the audit's estimate is that this trims roughly
a third of total spend, and even a conservative outcome is a meaningful cut.

Where: model.ts, poller.ts ([AUTO] spawn), the [AUTO] prompt templates, tests.
Effort: S. Verify: a week of usage_log after deploy, compare the kind=auto
slice; read a few nightly summaries for quality regression and revert per-job
if haiku's are noticeably worse. Depends: nothing.

### 1.2 Meter the review loop

What: review.ts spawns claude directly with stdout ignored, so its roughly 18
runs a week never reach usage_log; the spend tracker undercounts by design.
Haiku-cheap, but the point of the meter is that it is complete.

How: add --output-format json to reviewSpawnArgs, capture stdout in the
existing exited handler, parse total_cost_usd and tokens, and insert a
usage_log row with kind=review. Fire-and-forget semantics stay.

Where: review.ts, db.ts (only if the insert helper needs a kind), tests.
Effort: S. Verify: trigger a review pass, see the row. Depends: nothing.

### 1.3 /usage command, plus a weekly cost line

What: a poller-handled command (like the /quiz family: answered from SQLite
directly, no claude spawn, instant and free) that prints today / 7 days / 30
days spend, split by model and kind, from usage_log. Optionally the Sunday
[AUTO] job gains one weekly-total line. Complements the existing overspend
heads-up pings, which stay.

Where: poller.ts command branch, a small aggregate helper next to the usage
code, tests.
Effort: S. Verify: /usage in chat matches a manual query. Depends: 1.2 if the
numbers should include the review loop (do 1.2 first).

### 1.4 Commit the billing fallback runbook

What: the July-3 research produced a prepared fallback (env-flip to an API
key, the haiku lever, an OpenRouter plan B) that exists in memory notes but
not in the repo. Write it down as docs/runbooks/billing-fallback.md with the
trigger ("when Anthropic's notice email lands") and the exact steps.

Effort: S (docs only). Verify: read-through. Depends: nothing.

## Phase 3: quiz at full strength

### 3.1 The 554-question drop-in

What: the friend's 554-question bank replaces/extends the 80 starter
questions. The schema is compatible per the quiz guide and a data-sanity test
already guards the file.

How: a one-off import script (scripts/import-questions.ts) that validates the
schema field by field, deduplicates against the existing 80 (by id and by
normalized question text), normalizes topics and ids, checks Hebrew/RTL text
renders sanely, and writes the merged data/questions.json. Then bun test (the
sanity test), deploy, and a /quiz spot-check of a handful of questions.

Where: scripts/import-questions.ts (kept, so future banks reuse it),
data/questions.json.
Effort: S once the file is in hand (M if the file turns out messy).
Depends: receiving the actual file (open question 4). Verify: test suite plus
manual /quiz sampling across topics.

### 3.2 Quiz stats (small, optional)

What: /quiz_stats as a poller-owned command: streak, questions answered per
week, accuracy by topic, weakest topic. Reads quiz-state.json / the journal;
no claude spawn. High daily usefulness while interviewing; minor demo value.

Effort: S. Depends: nicer after 3.1 (topic variety). Verify: numbers match a

## Phase 4: hardening (debt with a clear payoff)

### 4.1 Schema versioning and migrations in db.ts

What: db.ts hardcodes the schema; changes so far were hand-done additive
columns. The first breaking change, or the first restore of an old backup
onto newer code, will hurt. A user_version (or meta table) plus an ordered
migration list, run at open, is about half a day and pairs naturally with
0.1: restore is only safe when the code can upgrade an older file.

Where: db.ts, a migration test with a fixture db.
Effort: S. Verify: open an old-schema fixture, assert upgraded shape.

### 4.2 poller.ts extraction policy

What: 2,177 lines and the highest churn in the repo (48 of 221 commits). Not
a big-bang refactor; a standing rule instead: whenever a change touches one
of the four remaining big chunks (attachment pipeline, prompt assembly,
callback routing, scheduler loops), extract that chunk into its own tested
module first, in the same PR or the one before. The existing extractions
(dispatch, stream, quiz, choices) set the pattern. Soft target: poller.ts
under ~1,500 lines by the time this roadmap is done.

Effort: amortized across other items. Verify: line count trend, tests stay
green.

### 5.1 Guard approval buttons

What: today the guard has two answers, hardline-deny or allow. This adds the
middle tier from the survey's A1: a list of risky-but-not-hardline command
patterns that the hook denies with "propose this to Maor", the agent then
registers a confirm.ts-style proposal, and a ✓ tap lets the exact frozen
command run once. The callback and confirm infrastructure this needed in June
has existed since PR #24, so the surveyed effort shrinks.

Guardrails: start with a handful of patterns, not 47; [AUTO] sessions stay
fail-closed with no approval path (the survey explicitly warns against
hermes's fail-open non-interactive behavior); approvals expire like calendar
proposals.

Where: guard.ts (pattern split), hooks/pretooluse-guard.ts, an approvals
state file, confirm.ts reuse, golden-list tests.
Effort: M. Verify: golden tests both ways, a live tap on the droplet.

### 5.2 /update from the phone

What: a Telegram command that, behind a ✓ confirm tap, runs the deploy path
(fetch, reset to origin/main with the existing autosave net, restart via the
graceful drain) and reports "back up, running <commit>". Plus a crash
breadcrumb: on boot after an unclean exit, the agent says so. With 0.2 in
place the loop becomes: alert arrives, tap /update or /restart, done, no
laptop.

Where: poller.ts command branch + confirm.ts, deploy.sh reuse, a breadcrumb
file, DEPLOY.md note.
Effort: S to M. Verify: run it for a real deploy of one of this roadmap's
PRs.

### 5.3 Webhooks: GitHub events trigger the agent

What: a small Bun.serve listener with HMAC verification (GitHub
X-Hub-Signature-256), named subscriptions, a prompt template rendered from
the payload, delivered through the existing [AUTO] pipeline. First real
subscription: push and CI-failure events on this repo, so a red main run
pings Maor with a one-line summary.

Exposure care: high port with HMAC as the gate and fast drops for
non-matching requests, or localhost behind a reverse proxy; decide at
implementation, document the threat model either way. Fire-time threat scan
on rendered payloads (the survey's own lesson from hermes bug #3968).

Where: new webhook.ts + tests, systemd/env for the port and secrets,
DEPLOY.md.
Effort: M. Verify: a signed test delivery from GitHub's redeliver button, a
forged-signature request rejected. Depends: 2.1.

## Suggested order of work

Wave A, about 1 to 2 days: 0.1, 0.2, 0.3 (one small PR each), then 1.1 + 1.2
together (same neighborhood), 1.4 alongside.
Wave B, about 1 to 2 days: 2.1 first, then 2.2, 2.4, 1.3, and 2.3 last so the
README describes a repo with CI, backups, and liveness already true.
Wave C, whenever the file arrives: 3.1, then 3.2 if wanted.
Wave D, about a day: 4.1 (4.2 is a standing rule, not a wave).
Wave E, per the green light: 5.1, then 5.2, then 5.3.

Total: roughly 7 to 10 working days of sessions, spread out. Every wave ends
deployed and useful on its own; there is no point of no return anywhere.

## Not doing, and why

- More monitors features, more routing keywords, more skills surface: the
  unused-surface data says the existing ones already outrun demand.
- Provider or model-gateway migration: the billing decision of 2026-07-03 is
  to stay put until Anthropic's notice email lands; 1.4 keeps the fallback
  warm instead.
- Host migration: decided 2026-06-15, staying on DigitalOcean; the card is on
  file and the cost is known.
- Multi-user pairing, kanban fleets, browser automation, image generation,
  external memory providers: the survey's section G rejections stand.
- A big-bang poller rewrite: 4.2's incremental rule instead.
