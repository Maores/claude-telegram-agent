# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Stack

Existing codebase: Bun + TypeScript, zero runtime npm dependencies by design.
The backlog view is a single static HTML file with inlined CSS and JS, written to
`docs/backlog-view.html` by `scripts/backlog-view.ts`. There is no build step, no
bundler, no framework, and no network at render time — the page is opened from
disk. Any design must survive those constraints.

## Users

One user: Maor, the sole developer and sole reader. He opens the page on a
desktop computer, never on a phone (confirmed 2026-08-27). He is not inside the
work when he opens it — he arrives cold, often days after the items were filed,
and needs to re-enter context quickly.

## Product Purpose

The page is the readable face of `docs/BACKLOG.md`, the ledger for the Telegram
agent project. It exists to answer one question on arrival: what needs a decision
from me. Everything else — approved work, frozen items, finished history — is
secondary and stays behind a filter.

Success is that he opens it, sees what is waiting on him, and either decides or
closes the tab. Failure is a page that leads with everything ever done.

## Positioning

The ledger is the source of truth and the page is only a projection of it. The
page holds no state of its own: counts, ordering and filters are all derived at
generation time, so the view cannot drift from the ledger. This is a deliberate
correction of the sibling project it is modelled on, where a hand-maintained
view and a hand-maintained markdown file disagree and collide.

## Operating Context

Items are filed by Claude sessions during health sweeps and audits, always as
`proposed`. Only Maor moves an item to any other status; a session may never
triage. So the page is read at the moment a decision is owed, not during work.

Regenerated by hand after the ledger changes:
`bun run scripts/backlog-view.ts`

## Capabilities and Constraints

- Hebrew, right-to-left. Mixed Hebrew and Latin runs are a real rendering hazard
  on this project and require isolated LTR islands for ids, paths and commands.
- Five statuses, in reading priority: needs a decision, approved, frozen, exists,
  closed. The status labels are a user interface, not a taxonomy — they get
  rewritten whenever one of them misleads Maor.
- Every item carries: an immutable id, a one-line title, its domain section, a
  size, a "how we will know it is done" line, and an optional history block that
  accretes dated updates rather than being rewritten.
- The page must work offline from `file://`, with no external fonts, scripts or
  images.
- Seven items today, across four domain sections. The design has to look right at
  that size and still hold at several dozen.

## Brand Commitments

- The project is called "Telegram agent", never "bot" (standing preference).
- Hebrew is the language of the ledger and the page, including item text, table
  headers and status tokens. The markdown is not an English file with a Hebrew
  skin; Maor reads and edits both.
- **Standing visual preference, chosen 2026-08-27:** the conventional issue-list
  convention, executed straight, with a GitHub issue page as the named craft bar.
  Maor was shown four rendered directions and picked this one deliberately over
  three distinctive alternatives. Future work on this surface holds that
  convention at full fidelity rather than smuggling in expression; if the look is
  ever to change, it is his call to make, not a session's.
- Nothing private may appear: the repository is public, so item wording describes
  problems technically without quoting personal content.

## Evidence on Hand

The seven seeded items are real findings from the 2026-08-27 health sweep and a
sanitization audit, each with its own provenance and reasoning recorded in the
ledger's detail blocks. No placeholder or invented content exists in the data.
